Snappet Cloud Connect

Two jobs hide inside this idea, and they need different machinery: keeping a clip playable when its file is no longer on the phone, and keeping Snappet's own records safe off the phone.

Split it into two featuresA media resolver that finds missing clips, and a backup that copies Snappet data to one chosen cloud. They share a settings screen, nothing else.
iCloud Photos needs no "connect"Snappet already reads the same library through PhotoKit. Missing originals are fetched by flipping one flag and storing a cross-device identifier.
Google Photos cannot be a silent fallbackSince March 2025 its API only returns items the app uploaded, or items the person hand-picks. Use Google Drive for automatic copies.
Back up by snapshot firstThe suite backup file already exists and encodes to identical bytes for identical data. Upload that automatically before attempting live sync.

What each service can actually do

The matrix is asymmetric. Apple gives on-device apps the whole library; Google gives third-party apps almost none of it.

Google PhotosOnly by handOwn uploads only The Picker API opens a Google-hosted picker; the person selects items and Snappet downloads them. Snappet cannot search or list the library by itself.
iCloud Drive / CloudKitIf Snappet stored a copyYes App container in the person's iCloud. No sign-in screen. Apple's review rule 5.1.3 restricts health information in iCloud, so heart-rate samples need care.
Google DriveIf Snappet stored a copyYes Google sign-in with the narrow drive.appdata (hidden app folder, for data) and drive.file (a visible Snappet folder, for media copies) scopes. Works for Android later too.

A common trap on iPhone: the Google Photos app's "Free up space" deletes originals from the Apple library. Every SessionMedia.localIdentifier pointing at them goes dead, and Snappet cannot ask Google for them back unaided. That case is why the vault option below exists.

Proposed shape

Media resolver

One service every surface calls instead of touching PhotoKit directly. It tries each source in order and stops at the first hit.

  1. Local libraryThe asset is on the phone. Today's path.
  2. iCloud originalAsset exists, file is offloaded. Download with progress. Free, no account work.
  3. Re-matchIdentifier is dead. Try the saved cloud identifier, then capture time + duration + dimensions.
  4. Snappet vault copyOptional. A copy Snappet uploaded to iCloud Drive or Google Drive when the clip was tagged.
  5. Ask the personGoogle Photos picker or the system photo picker. Snappet verifies the pick against the saved fingerprint.
  6. UnavailableKeep the record, HR and stats. Reels skip the clip. Never crash, never silently drop.

Data backup

One protocol, two destinations. The person picks one; both hold the same encrypted file.

  1. Watch for savesAny SwiftData save marks the store dirty. Wait for a quiet moment or app background.
  2. Encode with SnappetBackupThe existing versioned Rows file. Same data gives the same bytes, so a hash tells us if anything changed.
  3. Encrypt on the phoneKey lives in the keychain (iCloud Keychain carries it to a new iPhone). The cloud never sees plain records.
  4. Upload through CloudVaultICloudVault or GoogleDriveVault. Keep the last few generations plus a small manifest: device, time, hash, format version.
  5. Restore deliberatelyOn a fresh install or when another device wrote a newer file, offer it. Replace-everything, as the manual restore does now.

Pure parts stay device-free and testable in SnappetTests: the resolver's source-ordering decision, the fingerprint matcher, the backup scheduler's state machine, and the manifest comparison. PhotoKit, Google sign-in and file transfer sit behind thin protocols in Services/.

State machines

Three small machines instead of one large one. Select a state to read what the person sees and what Snappet does, then follow a transition to walk a scenario.

Build order

1 · Resolver and iCloud originalsOne MediaResolver, cloud identifiers on SessionMedia, downloading and missing tile states. Nothing leaves the phone, so the privacy promise is untouched.
2 · Automatic iCloud backupScheduler, encryption, manifest, restore-on-install. No sign-in UI. First change to the on-device-only rule.
3 · Google sign-in and Drive backupSecond CloudVault. Needs Google OAuth verification and the first third-party SDK or a hand-rolled OAuth flow.
4 · Media vault and Google pickerOpt-in clip copies and the relink sheet. Largest storage and bandwidth cost, smallest audience.

Decisions to make before building

  • The on-device-only promise changes. The README, privacy policy and project.md all say health and media never leave the device. Phases 2 to 4 need a named, opt-in exception recorded in decisions.md, plus updated privacy copy and App Store privacy labels.
  • Heart-rate samples in iCloud. Guideline 5.1.3(ii) says apps may not store personal health information in iCloud, and Apple has not said publicly whether client-side encryption changes that. Recommended default: leave HealthKit-sourced samples out of the cloud file and re-read them from Apple Health on restore; confirm with App Review before including them.
  • Backup, not sync. A snapshot gives one phone a safety net. Two devices editing at once would need CloudKit-backed SwiftData, which rejects the six @Attribute(.unique) fields in the schema and requires optional relationships. Worth doing only if multi-device use becomes a goal.
  • Whether the media vault is worth it. For iCloud Photos users it duplicates what Apple already keeps. Its real audience is people who use Google Photos with "Free up space". It could wait until someone hits the relink sheet often.
  • Android parity. The Android backup is a different file format (SQLite-level JSON), so a Drive backup made on one platform will not restore on the other without a shared format.
