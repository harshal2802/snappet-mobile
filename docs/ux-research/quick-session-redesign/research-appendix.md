## The finding-set's central thesis — that best-in-class climbing logbooks converge on a SESSION → CLIMB/ROUTE → ATTEMPT hierarchy, and that Snappet's freeform flow should promote that hierarchy using primitives it already owns in the Kilter board flow — is well-supported and verified across multiple independent sources. The named source apps largely work as described. The sourcing is accurate for the structural claims (KAYA swipe-to-log, Stokt Quick Attempt, Kilter V/Font + attempt logging, TopLogger toprope/lead per-discipline grading, 8a.nu scoring hierarchy, Crimpd named-workout timer, 8a.nu website-only catalog). The one materially wrong citation is the "Mountain Project grade-slider usability research" — there is a Mountain Project UX case study, but it is about search/navigation, not grade sliders, and contains no such finding; that specific evidence is fabricated/misattributed (though the underlying UX principle that labeled discrete controls beat freetext is sound and the Snappet advice stands). One claim is slightly imprecise: KAYA's intensity zones are actually named Easy/Hard/Limit and computed on a %-of-max (1RM-style) basis derived from your 3 hardest sends over 90 days — not literally "warmup/hard/limit" naively relative to max grade — but the substance (zones derived from your max, surfaced live as session intensity) is correct. The applicationToSnappet advice is retained in full as requested; it remains actionable regardless of sourcing nuances.

**Top takeaways**

Snappet's flat-attempt-row freeform flow really is missing exactly the CLIMB layer the best apps separate, and Snappet already owns the right primitives (KilterLogEntry, KilterSessionStats, KilterAscentStatus, StopwatchView, LiveMetricsPanel) to promote that hierarchy into the routineless logbook. Proceed with the redesign as specified.

Keep the scale-aware discrete grade-picker + recent-grade-chips recommendation (the UX principle is sound), but do not cite Mountain Project grade-slider research as evidence.

## The fastest gym loggers (Strong, Hevy, Fitbod) treat set logging as high-frequency data entry and minimize taps-per-set via last-time prefill (confirm-not-type), a checkmark that commits the set AND auto-starts a per-exercise rest timer, fast numeric entry with plate math available without leaving the field, and a searchable recents-first catalog with inline custom-exercise creation. Climbing-native apps (KAYA, Bould) add structured scale-aware grades that unlock pyramids and intensity zones. The redesign should map gym apps' two-level hierarchy (exercise -> sets) onto climbing's natural two-level hierarchy (named CLIMB/ROUTE with type+grade -> attempts), make catalog/create-custom the entry point for both climbs and timed exercises, prefill from the existing Kilter models, and reuse StopwatchView + command bar + LiveMetricsPanel — with the primary action being confirm, not type. The fact-check confirms nearly every claim; the one nuance is that the specific "persistent custom keypad that never animates" framing is only partly documented (Hevy references the system keyboard).

## A timed-exercise / climbing-logging flow is strongest when it (1) models a named, typed PARENT object (a climb/route, or a named timed exercise like "20mm repeaters") with individual efforts/attempts/hangs nested UNDER it, and (2) cleanly separates two timer mentalities — a structured pre-programmed interval runner (work/rest/sets/reps with a 3-2-1 lead-in, distinct per-phase audio + haptic cues, and glanceable now/next/progress) versus a freeform open count-UP stopwatch for a single effort. Selection-vs-creation should be one low-friction decision; the timer measurement itself should BE the log. The source apps (Crimpd, hang!, HangTight, Seconds Pro, Intervals Pro, Box Timer, Tindeq) broadly bear this out — and Tindeq is the verified cautionary tale of flexibility without a guided default. For Snappet, generalize the existing rich Kilter models (KilterLogEntry/KilterSessionStats) to freeform climbing AND timed exercises, reuse StopwatchView/Glass HUD/LiveMetricsPanel, and add a structured interval engine on a catalog-vs-create entry point. The applicationToSnappet advice holds regardless of sourcing precision.

**Top takeaways**

- No pattern is refuted — the finding-set is unusually well-sourced. The four riskiest/most-specific claims spot-checked all held up, several near-verbatim: Tindeq's '10s→20s' silent rewrite and 'too clunky to be useful' (App Store reviews), Box Timer's three-mode count-up/count-down/interval split (its own copy), Seconds Pro's compound timers + color-coding 'know what is coming before the beep' + TTS advance-warning, and Intervals Pro's 3s prep that 'allows Apple Health tracking time to warm up' + wrist-tap-at-interval-end.

## Snappet's freeform "Quick Session" is a grow-as-you-go logbook whose live-feedback problem differs from a guided-workout app: there is no plan to track against and the user's body is busy (especially on the wall).
