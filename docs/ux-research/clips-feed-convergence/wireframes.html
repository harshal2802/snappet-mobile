Clips ⇄ Studio — one clip, one truth

The convergence (prompts 116 + 117): "Edit this clip" already saves everything in place (the Studio project persists on every edit and the feed already rebuilds when it changes) — but today only the tile's style flows back. Three lanes close the gap: ① live-reflect — the feed plays trims (loops the kept range, poster = the trimmed first frame) and draws the extended HR window (lead/tail panes · scope · parked dot — the export's chart); ② bake — an explicit "Save to original" renders the FULL edit (speed · filters · text · overlays) into the Photos asset itself, revertible or space-freeing; ③ export as new — today's flow, untouched. What can't play live without a per-cell composition is never faked — it's baked or exported.

2 · What reflects — the honest tier model

✓ Reflects in the feed (this prompt)

  • Trim — inline player loops the kept range (AVPlayerLooper timeRange); fullscreen transport spans it; poster = first kept frame; HR footage-span = the trimmed window (dot stays in sync because playback is trimmed too)
  • Extended HR window — lead/tail panes + boundary ticks, dot parks at the footage/tail boundary, per-clip stored values (defaults 0:05/0:30 when never edited / no project)
  • Metrics scope — AVG/PEAK per Clip-only or Full-window, matching the export
  • Tile style — template/metrics/colours (already shipping, prompt 89)
Cheap: pure re-slicing + player range args. The chart machinery (panes, keyframes, scope) shipped in prompt 115 and is shared.

◉ Reflects after a BAKE (lane ② — prompt 117)

  • Speed · filters · colour adjust · crop
  • Text / sticker / climb-name overlays · PiP · transitions · music · burned HR tile
  • Rendered ONCE at "Save to original"; the feed (and every other app) then plays the baked pixels — full parity with zero per-cell composition cost
Live playback of these needs an AVComposition + compositor per feed cell (the Core-Animation overlay tool is offline-only — even the Studio preview fakes overlays as a SwiftUI layer). Baking pays the render once at save-time instead of every playback (prompt 97/106 carousel-perf work stays intact).

✗ Never reflects (deliberate)

  • Tile placement/size in the LIVE overlay — the feed keeps its uniform bottom strip (legibility + scroll perf); a baked clip carries your placement in the pixels
The feed is a feed, not a canvas — uniform placement is a product decision, unchanged since prompt 82/89.

4 · The bake lane — "Save to original" (prompt 117)

The Studio's Export button becomes a three-destination menu. Baking renders the full edit (trims · speed · filters · text · burned HR tile) into the Photos asset — pay the render once, and every surface (this feed, Messages, Photos) shows it. Storage honesty: the revertible variant KEEPS the original bytes (Photos' non-destructive model — a trim adds a rendition, it never frees space); only the destructive variant reclaims space, after the system's Recently-Deleted 30-day purge.

5 · Rules & edge cases

Behavioural rules

  • No project / never edited → raw clip + default HR window (0:05/0:30, Full-window scope) — the same defaults the Studio would apply.
  • Split clips (one video → two timeline clips with adjacent trims): the feed shows the kept envelope [earliest trimStart … latest trimEnd] — one feed item per physical asset stays the rule.
  • Clip removed from the project ≠ removed from the feed: the feed falls back to the raw clip (a Studio edit must never hide feed media).
  • Still poster & at-end reading: poster frame at trimStart; the poster's BPM parks at the footage/tail boundary (last on-camera reading), never the tail end — the peak label covers the tail.
  • Trim sanity: a degenerate trim (≤0.5 s kept) is ignored in the feed (plays raw) rather than looping a blink.
  • Reactivity: existing FeedKey.updatedAt path; returning from the scoped Studio recomposes the feed (200 ms debounce, off-main).

Bake-lane rules (prompt 117)

  • Baked flag: a bake stamps SessionMedia.isBaked — the feed's live HR overlay stands down (name tag only), trims/window live-reflect is skipped (the pixels already carry the edit), and the poster regenerates.
  • Revertible bake (PHContentEditingOutput): Photos keeps the original bytes — "Revert to Original" (in Photos, or via an app affordance) restores them; the app then clears isBaked on next reconcile (rendition change detection). Storage: original + rendition both kept — a trim never frees space on this path.
  • Replace (destructive): save-as-new + delete-original. iOS shows its own deletion confirm; the original sits in Recently Deleted for 30 days before space frees. The app re-points the clip's SessionMedia.localIdentifier (and the Studio project's clip) to the new asset in the same transaction — session detail, feed, and project follow automatically; the offset/duration update to the trimmed length.
  • Re-editing a baked clip: the Studio project is untouched by a bake, so "Edit this clip" resumes exactly where you left off; re-baking overwrites the rendition (revertible path) or repeats the replace flow.
  • Requires Photos read-write authorization (the app already requests it for discovery; a bake prompts an upgrade if the user granted limited access).
  • Never automatic: baking is tied to the explicit Export-menu action, never to per-edit saves (each bake is a full re-render).
