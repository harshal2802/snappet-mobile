Kilter UX feedback — four fixes

A real climber used the Kilter mini-app and hit four walls. Each flow below shows the fix on the Pulse Pro language (kilter amber #F59E0B wayfinding, coral CTA, dark-mode-first, real SnappetColor tokens). F3 is mostly a logic fix — its wireframe shows the behavior contract, not new chrome.

1. “Connecting to the board was hard to see” — the only Connect button lives 8 blocks deep in a climb's detail scroll; the browse screen has no connection surface at all.
2. “Filtering was not obvious” — filters are split across a chip row that looks like static text, a toolbar icon, and a search field hidden until you pull down.
3. “Resets board to 12 x 14” — the size preference is one global value; any layout switch (or a transient catalog reload) stomps it back to the layout default.
4. “Most recent climbs takes a lot of screen real estate on the list” — the re-light rail is ~200 pt tall and always expanded, leaving ~3 climb rows visible.
Flow F1 · Board connection you can actually see

One persistent board strip on the browse screen

Today board.connect() is only reachable from illuminateSection — the 8th block down the climb-detail scroll (below the render, legend, angle picker, stats, logging and the grade chart). The fix: the root's session slot becomes a board + session strip — connection state (gray / pulsing amber / green) with a one-tap Connect, next to Start session. The climb detail mirrors state in a glass pill on the board render itself, so "am I connected?" is answered where the climber is looking. No new screens; the strip reuses the existing KilterBoardController.state machine.

Flow F2 · Filtering that looks filterable

One Filters entry, chips that read as controls, search always visible

Today the criteria are split three ways: five look-alike chips (Layout · Size · Angle · Min · Max), a toolbar funnel icon for the other four criteria, and a search field hidden behind a pull-down (navigationBarDrawer(displayMode: .automatic)). The fix: (a) search pinned always-visible; (b) a leading ⛛ Filters chip with a live active-count badge as the single obvious entry; (c) chips get ▾ affordances and merge — Layout+Size into one Board chip, Min+Max into one Grade range chip; (d) the sheet gains the quick criteria too, with a live “Show N climbs” apply button so narrowing is felt immediately.

Flow F3 · A board size that sticks

Per-layout size memory — never silently reset again

Root cause found in code: the size is ONE global key (kilter.productSizeId), and syncBoardSize() (run on appear and on every layout change) overwrites it with the layout default — the lowest product_size_id, i.e. “12 x 14” — whenever the stored size isn't valid for the current layout, including the moment the catalog hasn't finished loading (empty size list → forced reset). The fix is behavioral: store the choice per layout (kilter.productSizeId.<layoutId>), resolve staleness at read time via the existing effectiveSizeId instead of overwriting the preference, and skip the guard entirely while the catalog is unavailable. The wireframe shows the contract the tester expected.

Flow F4 · Give the list its screen back

“Recently on the board” collapses to a 36 pt chip strip

Today the re-light rail renders full cards — a 110 pt board thumbnail + name + status chip + a Re-light button — ~200 pt of chrome that appears whenever the climber has ever lit a hold, on top of the session bar and count line. On a 6.1″ phone that leaves ~3 climb rows visible. The fix: the rail becomes a single-line chip strip (status dot + name + ⚡ re-light), and the full-card experience moves one tap away — it already exists as the On the Board screen. Tap a chip → open the climb; tap its ⚡ → re-light without leaving browse.

Scope & sequencing

F3 (size memory) is the smallest and highest-anger fix — pure logic + tests, no visual risk. F4 (compact rail) and F1 (board strip) touch the same root-view real estate and land best together. F2 (filters) is the largest; its chip merge (Board, Grade) can ship first with the sheet unification as a follow-up. Each fix ships as its own PDD prompt + PR per pdd/README.md; the knowledge graph (docs/knowledge-graph/data.js) is updated with the changed browse/detail surfaces in the same change.
