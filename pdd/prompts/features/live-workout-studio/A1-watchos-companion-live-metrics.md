# Prompt: watchOS companion + live workout metrics relay

**File**: pdd/prompts/features/live-workout-studio/A1-watchos-companion-live-metrics.md
**Created**: 2026-06-01
**Project type**: Native iOS + **new watchOS** feature (Swift / SwiftUI) — code lands in this repo.
**Chain**: `live-workout-studio/PLAN.md` → Track A → **A1** (the unblocking foundation).
**Source**: GitHub issue [#15](https://github.com/harshal2802/snappet-mobile/issues/15); `RESEARCH.md` §3.1–3.2.
**Context**: `pdd/context/project.md`, `conventions.md`, `decisions.md`, `snappet-core-schema.md`.

## Goal

Give WorkoutTracker a **live metrics source**. Add a watchOS companion app that runs an
`HKWorkoutSession` + `HKLiveWorkoutBuilder`, and relays live heart rate (+ active energy) to the iPhone
over `WCSession`. The phone can **start the workout on the watch**, choosing the `HKWorkoutActivityType`
from the routine's sport/category. This is the one foundation that unlocks live metrics (#3), the
watch-trigger (#4), and background execution (#1) together — everything else in Track A and the live
parts of Track B build on it. Per `RESEARCH.md` §3.1, a watchOS companion is the *only* supported way to
get live Apple Watch HR and to start a workout on the watch.

## Context the implementer needs

- WorkoutTracker has **no HealthKit today** (`decisions.md` 2026-05-31 "separate suite app"). The flagship
  Reels app's `HealthKitService` is **post-hoc only** — do not entangle this with it; this is a new live path.
- A `WorkoutSession` (`WorkoutModels.swift`) already exists with `startedAt`/`completedAt`; the live
  session's HR must be storable against it (offsets relative to `startedAt`) so B2/B4 can consume it.
- There is **no watchOS target yet** — `ios/App/project.yml` (XcodeGen) currently builds the iOS app only.
  This prompt adds the target; the project is generated by `xcodegen generate` (don't hand-edit `.pbxproj`).
- The rest timer already uses the **end-`Date`** pattern that survives backgrounding — reuse that mindset;
  do not introduce a wall-clock-naive timer.
- This supersedes the v1 "post-hoc only / no watchOS" deferral **for WorkoutTracker** — note it in
  `decisions.md` (`RESEARCH.md` §5), it does not change the flagship Reels app.

## Approach

Respect the layering rule — `HighlightEngine` stays platform-free; all platform I/O is a `Services/` type.

**watchOS target (new `ios/App/SnappetWatch/`, wired in `project.yml`):**
- `WorkoutWatchManager` — owns `HKWorkoutSession` + `HKLiveWorkoutBuilder` + their delegates; starts/ends
  a session for a given `HKWorkoutActivityType`; publishes latest HR/energy; registers the watchOS
  workout-processing background mode so HR keeps flowing when the wrist drops.
- `WCSession` link (`WatchConnectivityLink`) shared shape with the phone: messages
  `start(activityType)`, `stop`, and streamed `metrics(hrBpm, energyKcal, t)`.
- Minimal watch UI: current HR + elapsed + a Stop button (start is normally driven from the phone).

**iOS side (new `Services/LiveWorkoutService.swift`):**
- `WCSession` host; `@Observable @MainActor` exposing `latestHR`, `energy`, `isWatchReachable`,
  `connectionState`.
- `start(for: Routine/WorkoutSession)` → maps `SportTag`/category → `HKWorkoutActivityType`, sends
  `start` to the watch. `stop()` ends it.
- Buffers incoming samples into `HRSample`s (t = seconds since `session.startedAt`) for later persistence
  (B2/B4). Keep the buffer here; persistence of a per-session HR series can land with B2.
- A `WorkoutActivityMapping` helper (routine sport/category ⇄ `HKWorkoutActivityType`), the inverse of
  `HealthKitService.map`.

Wire `LiveWorkoutService` into `AppModel` (the single engine/services meeting point), injected via
`.environment`. No UI overlay yet (that's A4) — A1's iOS deliverable is the service + the watch-trigger +
a debug readout proving samples arrive.

## Output

- `ios/App/SnappetWatch/` — watchOS app: `SnappetWatchApp.swift`, `WorkoutWatchManager.swift`,
  `WatchConnectivityLink.swift`, a minimal `WatchWorkoutView.swift`, `Info.plist`, entitlements
  (HealthKit + workout-processing background mode).
- `ios/App/project.yml` — new watchOS target + the iOS app's watch-companion embed; HealthKit entitlement
  on the watch target.
- `ios/App/Snappet/Services/LiveWorkoutService.swift` — phone-side WCSession host + start/stop + HR buffer.
- `ios/App/Snappet/Services/WorkoutActivityMapping.swift` — sport/category ⇄ `HKWorkoutActivityType`.
- `ios/App/Snappet/Core/AppModel.swift` — own + inject `LiveWorkoutService`.
- A temporary debug readout in `WorkoutPlayerView` (behind a small `#if DEBUG` or a plain row) showing the
  latest relayed HR, to prove the pipe end-to-end before A4 builds the real overlay.
- `pdd/context/decisions.md` — the "WorkoutTracker gains a live watchOS path (supersedes v1 post-hoc-only
  for this module)" entry.

## Acceptance criteria

- [ ] `xcodegen generate` produces a project with **both** an iOS app and a watchOS app target; both
      compile for their simulators (Swift 6, 0 warnings).
- [ ] The phone can send `start(activityType)` to the watch; the watch begins an `HKWorkoutSession` of the
      mapped type; HR samples stream back over `WCSession` and appear in `LiveWorkoutService.latestHR`.
- [ ] Routine sport/category maps to a sensible `HKWorkoutActivityType` (e.g. climbing→`.climbing`,
      cardio→`.running`/`.other`, strength→`.traditionalStrengthTraining`), with an `.other` fallback.
- [ ] HR samples buffer as engine `HRSample`s with `t` relative to `session.startedAt`.
- [ ] No platform imports added to `HighlightEngine`. Live HR is converted to plain value types at the
      `Services` boundary, exactly like the post-hoc path.
- [ ] `decisions.md` updated; the change is scoped to WorkoutTracker (flagship Reels unchanged).

## Constraints

- On-device only; no backend/network/accounts. **No Fitbit/Google cloud** — see `RESEARCH.md` §3.3.
- Keep the source pluggable: shape `LiveWorkoutService`'s output so A3 can extract a `MetricsSource`
  protocol with a BLE conformer **without** changing call sites (mirror the `HighlightSelector` pattern).
- State verification honestly: a clean type-check / sim build is necessary but **not** a device run —
  live HR + WCSession + the watch session only truly run on a **paired physical Apple Watch + iPhone**
  (`RUNBOOK-device.md` territory). Do not report the relay as "verified" off a build alone.

## Test plan

1. `xcodegen generate` then `xcodebuild` both targets for their simulators → BUILD SUCCEEDED, 0 warnings.
2. Unit-test the pure pieces with no device: `WorkoutActivityMapping` (sport/category → type) and the
   HR-buffer offset math (sample wallclock → `t` since `startedAt`). These belong in the app's test target
   (not `HighlightEngineTests`, which stays platform-free).
3. **Device gate (user step, document don't fake):** on a paired Apple Watch + iPhone, start a routine →
   confirm the watch starts the session, HR appears on the phone within a few seconds, and it keeps
   updating with the phone backgrounded. Capture the latency/battery observation for the PLAN's "after A1"
   decision gate.
