## Goal

A garment is not one photograph. The closet stores exactly one image per item, so the back of a
graphic tee, the care label, and what the thing actually looks like on a person all have nowhere to
go. Let a garment carry **up to six photos**, each with an optional role, addable during capture or
later, and browsable as a swipeable hero — without slowing down the one-photo path that already
works, and without a migration.

## Context the implementer needs

- **This sits on wardrobe prompt 03.** `WardrobeImageStore.prepare(image:isCutout:)` already returns
  a capped display master (≤1024px) plus a thumbnail (≤320px), and `WardrobeImageCache` already
  decodes off-main through a cost-bounded `NSCache`. **Every new photo must go through that same
  pipeline** — a photo written any other way re-creates the 1.01 GB bug prompt 03 just fixed.
- **`WardrobeCaptureSheet`** is a three-stage flow (`pick` → `processing` → `review`) that today holds
  a single `original`/`cutout` pair in `@State` and writes them in `save()`.
- **`WardrobeItemTile`** renders at nine sites (38pt…100pt) and reads the item's **cover** thumbnail.
  It must stay a single-row read — see the storage decision below.
- **CloudKit-compatibility is locked** (prompt 01): inline defaults or Optional on every stored
  property, no `@Attribute(.unique)`, no SwiftData relationships — plain UUID FKs, flat tables.
- **Adding a `@Model` REQUIRES a mirror Row in `Core/SnappetBackup.swift`**;
  `SnappetBackupTests.testCodecCoversEverySchemaModel` is the tripwire. Follow prompt 03's split:
  masters ride the backup, **thumbnails do not** (derived data, regenerated by the migration path).
- **`WardrobeVision.liftSubject`** is the background-removal edge. Whether to run it is now a
  per-photo decision (see roles), not a global one.

## Approach

- **Pure vocabulary** — `GarmentPhotoRole` in `WardrobeTags.swift`: `front, back, worn, tag, detail`.
  A **closed** enum on purpose, even though prompt 05 (P3) makes other dropdowns extensible: role
  drives real behavior (`shouldLiftSubject` — false for `worn` and `tag`, where you want the person
  and the label, not a silhouette), so an arbitrary user string would have no defined semantics.
- **Storage** — a new `WardrobePhoto` `@Model`: `id`, `itemID: UUID?`, `roleRaw`, `sortIndex`,
  `@Attribute(.externalStorage) imageData`, inline `thumbnailData`, `createdAt`.
  **The COVER photo deliberately stays on `WardrobeItem.imageData`/`thumbnailData`.** Two reasons,
  both load-bearing: the closet grid renders 100 tiles and must never join a second table to do it,
  and it means **zero migration** — every existing garment is already a valid one-photo item.
  `WardrobePhoto` rows hold only the *extra* photos.
- **Pure ordering/promotion logic** — `WardrobePhotoSet` (new, pure, tested): given a cover + the
  extra rows, produce the ordered display list; decide the new cover when one is deleted; assign the
  next unused role; enforce the six-photo cap. Cover promotion is the subtle one — deleting the
  cover must promote the next photo and copy its bytes into the item's cover slots, never leave the
  garment photo-less.
- **Capture** — the review stage's single preview becomes a **strip**: cover first, then extra
  slots, then `+`. The `+` sheet asks **role first, source second**, because the role decides whether
  to run subject lift. Extra photos are stored and thumbnailed but **do NOT re-run tagging**: the
  tags were drafted from the cover, and a worn shot would drag the dominant-color average toward
  skin and background.
- **Detail** — the 240pt hero becomes a `TabView(.page)` over the ordered photos with a role caption
  and dots. **A one-photo garment must render exactly as it does today** — no dots, no caption, no
  new chrome. Reorder / re-role / set-cover / delete live in one **Manage photos** sheet reached from
  the ··· menu, not a long-press on the carousel (a swipe surface should only swipe).

## Acceptance criteria

- [ ] A garment can hold up to 6 photos; the 7th add is refused with a visible reason, not silently.
- [ ] Saving with one photo behaves exactly as before — no extra taps, no `WardrobePhoto` rows.
- [ ] Every stored photo goes through `WardrobeImageStore.prepare`; grep proves no other write path.
- [ ] `worn` and `tag` photos skip subject lift; `front`/`back`/`detail` run it.
- [ ] Deleting the cover promotes the next photo; a garment with ≥1 photo never renders the emoji.
- [ ] A one-photo garment's detail hero shows no dots and no role caption.
- [ ] The closet grid still reads only `WardrobeItem` — no per-tile fetch of `WardrobePhoto`.
- [ ] `WardrobePhotoRow` added to `SnappetBackup` (tripwire green); thumbnails excluded as in prompt 03.
- [ ] Deleting an item deletes its `WardrobePhoto` rows (no orphans — there is no cascade, the FK is
      a plain UUID).
- [ ] App changes type-check against the iOS 18 SDK (Swift 6, 0 warnings).
- [ ] `decisions.md` + `docs/knowledge-graph/data.js` updated in this change.

## Constraints

- On-device only; no backend/network. CloudKit-compatible: inline defaults / Optional, no `.unique`,
  no relationships.
- Storage budget is the reason for the 6-photo cap: at prompt 03's caps a fully-photographed garment
  is ~8 MB (still less than the 10 MB a *single* photo cost before prompt 03), and a 100-item closet
  at 3 photos each lands near 390 MB. State this in `decisions.md`, not just in review.
- State verification honestly: camera capture and the Photos picker are **device-only** legs.
