# Prompt: Ship prep — privacy manifest, app icon scaffold, display name, hardening review (P7)

**File**: pdd/prompts/features/07-ios-ship-prep.md
**Created**: 2026-05-31
**Project type**: Native iOS feature (Swift / SwiftUI, XcodeGen).
**Chain**: `pdd/prompts/features/PLAN-ios-to-shippable.md` → P7
**Source**: [Snappet#60](https://github.com/harshal2802/Snappet/issues/60) §7 (App Store prep / privacy).
**Context**: `pdd/context/project.md`, `pdd/context/conventions.md`, `pdd/context/decisions.md`

## Goal

Get the app to a submittable state: ship the Apple **privacy manifest**
(`PrivacyInfo.xcprivacy`), scaffold the **app icon** asset catalog, set the
**marketing display name**, wire all of it into the XcodeGen spec so the project
still regenerates cleanly, and do a light **empty/error-state hardening review**
for shippability. No backend, no analytics — the app stays fully on-device, which
shapes the privacy declaration.

## Context the implementer needs

- The project is generated by XcodeGen from `ios/App/project.yml` — never hand-edit
  the `.pbxproj`. Anything under `Snappet/` is already a source path, so a privacy
  manifest and an asset catalog dropped there are picked up automatically; only the
  app-icon **name** has to be declared in build settings.
- The app transmits nothing. Health (heart rate) and Photos/Videos are read,
  processed into a reel, and written back to the user's own library on-device. So
  the privacy manifest declares **no data collection** (Apple's "collected" means
  transmitted off device) and **no tracking**.
- The only "required reason" APIs the app actually exercises are:
  - **File timestamps** — `FeedbackStore` (JSONL training-data sink) and
    `ReelExporter` (temp output) touch timestamps on files the app itself created
    → category `NSPrivacyAccessedAPICategoryFileTimestamp`, reason **C617.1**.
  - **UserDefaults** — only the onboarding flag (`snappet.hasOnboarded`)
    → category `NSPrivacyAccessedAPICategoryUserDefaults`, reason **CA92.1**.
- Display name: `Info.plist` already carries `CFBundleDisplayName = Snappet`; also
  express it as a build setting so it survives if the plist is ever regenerated.
- App icon art can't be drawn here — scaffold the slot and document the drop-in.

## Approach

- **Privacy manifest** `Snappet/Resources/PrivacyInfo.xcprivacy`: a plist with
  `NSPrivacyTracking=false`, empty `NSPrivacyTrackingDomains`, empty
  `NSPrivacyCollectedDataTypes` (with an XML comment explaining the on-device
  rationale), and the two required-reason API entries above.
- **App icon catalog** `Snappet/Resources/Assets.xcassets/`:
  `Contents.json` (xcode/version 1) + `AppIcon.appiconset/Contents.json` using the
  modern single-size format (one `universal`/`ios`/`1024x1024`/`AppIcon.png`
  entry). No binary PNG; a `README.md` documents that a 1024×1024 no-alpha
  `AppIcon.png` must be dropped in before submission and the slot is intentionally
  empty until then.
- **XcodeGen** `project.yml` base settings: add
  `ASSETCATALOG_COMPILER_APPICON_NAME: AppIcon` and
  `INFOPLIST_KEY_CFBundleDisplayName: Snappet`. Leave deployment target (iOS 18.0)
  and `SWIFT_VERSION` (6.0) untouched.
- **Info.plist**: ensure `CFBundleDisplayName = Snappet` is present (already is).
- **Hardening review**: read the Features + `AppModel` and record findings (see
  "Hardening notes" below). Don't change Swift unless there's a real crash risk.

## Output

- `ios/App/Snappet/Resources/PrivacyInfo.xcprivacy` — the privacy manifest.
- `ios/App/Snappet/Resources/Assets.xcassets/Contents.json` — catalog root.
- `ios/App/Snappet/Resources/Assets.xcassets/AppIcon.appiconset/Contents.json` —
  single 1024×1024 icon entry.
- `ios/App/Snappet/Resources/Assets.xcassets/AppIcon.appiconset/README.md` —
  drop-in instructions for the missing PNG.
- `ios/App/project.yml` — `ASSETCATALOG_COMPILER_APPICON_NAME` + display-name setting.
- `decisions.md` entry: on-device → no privacy-label data collection; declared
  required-reason APIs (C617.1, CA92.1); single-size 1024 icon, art pending.

## Acceptance criteria

- [ ] `PrivacyInfo.xcprivacy` lints (`plutil -lint`) and declares no tracking, no
      collection, and exactly the two required-reason APIs the code uses.
- [ ] Both `Contents.json` files are valid JSON; the appiconset uses the single
      1024×1024 entry and references `AppIcon.png`.
- [ ] `project.yml` is valid YAML; deployment target / Swift version unchanged.
- [ ] `Info.plist` still lints and carries `CFBundleDisplayName = Snappet`.
- [ ] No Swift behavior change unless an actual crash risk is fixed (explain if so).

## Constraints

- XcodeGen-managed — don't touch `.pbxproj`. Keep `project.yml` valid YAML.
- On-device only; do not declare data collection or tracking that doesn't happen.
- Adding the real `AppIcon.png` and the actual TestFlight upload are out of scope
  here (no signing identity / art in this environment) — state that honestly.

## Hardening notes

Reviewed `Core/AppModel.swift` and `Features/**` (`WorkoutListView`,
`OnboardingView`, `ReelView`, `ReelViewModel`). The empty/error handling is already
shippable; **no crash risks found, so no Swift code was changed.** Specifically:

- **Every async surface is state-driven, not force-unwrapped.** `AppModel.Phase`
  and `ReelViewModel.State` are exhaustive enums the views `switch` over; errors
  funnel into `.error(String)` (typed `LocalizedError.localizedDescription`) and
  render via `ContentUnavailableView`. No `try!` / `!` force-unwraps on the async
  paths; `export()` / `buildPreview()` guard `workout`/`result` and return early.
- **Empty states are all handled**: no workouts → `ContentUnavailableView` overlay
  on the list; no clips → `.empty` state with a "Select clips" fallback (which also
  covers `.limited` Photo access); preview with no video → caught, friendly message.
- **Limited Photo access** has a real manual-picker path (`MediaPicker`), so the
  reel flow degrades gracefully rather than dead-ending.
- **Minor, non-crashing UX nits (left as-is to keep this phase Swift-disjoint):**
  1. `OnboardingView.connecting` is set `true` on tap but never reset to `false` if
     `completeOnboarding()` routes to `.error` (the button stays spinning under the
     error screen). Harmless because the error view replaces the screen, but worth a
     `defer { connecting = false }` in a future UX pass.
  2. `WorkoutListView` shows the "No workouts yet" overlay only in `.ready`; during
     `.onboarding`/`.loading` it shows a spinner — correct, just noted.
  These are polish items, not ship blockers, and are intentionally not changed here.
